# Changelog

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **The blocks and the modules are grouped by what you are designing.** One heading called "iSport" was the first step and not enough of one: thirty-two entries under it is a shorter list to scroll and still the wrong question to ask of it, because somebody in the builder is working on a trainer's page, or a kind of course, or a course, and wants the fields of that one thing. There are now three sections — **Courses** (21 blocks, 21 modules), **Kinds of course** (3 and 3) and **Trainers** (8 and 8) — and each block and module is filed by the context it already declares in the catalogue, so nothing has to be remembered twice.
- In Divi they are three folders inside the "iSport" one, because Divi keeps folders as a tree: the store files them under `path/name` and the list asks for the children of a path. In the block editor they are three sections side by side, named "iSport: courses" and so on, because WordPress's categories are a flat list and a block belongs to exactly one — the same arrangement WooCommerce uses, for the same reason.
- A test now refuses a module filed under a folder nobody registered, which would take it out of the list altogether rather than merely putting it in the wrong drawer.
- **The way into iSport is two modules now: a button and a link**, each the shape it claims to be. The first attempt at this was one module with a switch on it reading "button or plain link", and it was wrong in a way worth writing down: the switch changed a class name and nothing else. These modules are generated from one catalogue, so the Design panel was the one a text field gets — no Button group to reach, nothing for a page builder's button presets to attach to, and a switch that appeared to do nothing because it did nothing. The argument for it, that "a link and a button are the same element and the design panel is the same for both", was true of the markup and false of the builder, which is the only place the difference was going to show.
- The button now declares `elementType: button` with Divi's own `decoration.button`, exactly as Divi's Call To Action declares the button inside itself. That is what summons the whole Button panel — text, background, border, icon, hover — and the styles it writes land on the real element: verified by reading the generated stylesheet, `body #page-container .cscs_divi_field_course_button_0 .cscs-button.et_pb_button{background-color:…}`. It also carries `et_pb_button`, so button styling set for the site as a whole reaches it without being restated. The link declares none of that on purpose: it is an anchor in the text, styled by the theme's link styling, with a font, spacing and border group of its own — `.cscs_divi_field_course_link_0 .cscs-signup-link{color:…}`.
- **Both can say what you want them to say.** The wording could be changed on a display set and nowhere else, so a course page, a block and a Divi module all said whatever the plugin said. *Link text* on the module and the block now; content, not design, because it is words.
- **iSport → Settings gains "What the booking link says"**, which is what everything falls back to: the module, the block, the course page and any display set that has not been given wording of its own. The wording of the whole site is now one field, which is what was actually being asked for.
- A collision found on the way: the new control was labelled *Wording*, which the display-set screen already uses as a section heading and which Czech translates there as "Texty" — so the Divi panel came out reading "Texty" over a text box for the words on a link. gettext has no context to tell the two apart, so the label is *Link text* and the two strings are two strings.

## [1.0.0-alpha.2] - 2026-09-08

### Fixed
- **A third of the courses had quietly disappeared, and three separate complaints turned out to be one bug.** The remote course listing takes a date, and asked without one it answers with the courses whose first lesson is still ahead of this very moment — which on a term already three days old is 73 of the 113 courses this gym runs. Everything downstream believed that list. `archive_missing()` was handed it and archived the 40 that were not in it, so forty real courses vanished from every table on the site as "no longer offered by iSport". The matcher was handed it too, so every occurrence of those forty had no course to belong to: 219 unresolved out of the 1 848 stored. And a kind of course whose only courses had been archived had nothing left to take a description from, which is why *Gymnastika pro dospělé* and five others answered the Fetch button with silence. The listing is now asked for from the configured **Term starts**, less a month's margin, because a term does not begin on one single day: this gym's courses open across the first week, from Monday the 7th to Friday the 11th, and the office calls the 11th the start. The margin is a filter, `cscs_course_lookback_days`. After the fix: 105 courses, 0 wrongly archived, unresolved down from 219 to 57 — and of the nine names still unresolved, eight are courses iSport does not publish in its course listing at all, at any date.
- **A course iSport had stopped offering vanished from every listing and its own page stayed up.** Which is half a withdrawal: the course was unfindable and still perfectly readable to anybody holding last term's link, offering hours that no longer exist. It now goes into a state of its own — `Cancelled`, registered as a post status rather than borrowed from `draft`, because a draft is something somebody started writing and has not finished, and a year of withdrawn courses filed among them is a year of nobody being able to tell the two apart. The list of courses gains its own tab with its own count; everything written on the page is kept; and the course publishes itself again, on its own, the moment iSport offers it. A course somebody has trashed or deliberately left as a draft is left where they put it.
- The old address sends the visitor to **the kind of course the withdrawn one belonged to**, permanently. Not found is correct and unhelpful: somebody following a link from last term was looking for gymnastics for eight-year-olds, and the page listing the gymnastics still running answers that. Where the kind has no page, the not-found page stands — inventing a destination is worse than admitting the page has gone. `cscs_cancelled_course_redirect` decides otherwise.
- Opening a withdrawn course and pressing Update no longer quietly puts it back on the site: that is not something the editor asks about, it is a status of "publish" it sends whether anybody meant it or not, and the next synchronisation would have taken the page down again — so the page would appear and disappear with nothing saying why.
- **Three queries asked for courses in "any" status, which does not mean any.** WordPress reads it as "any status not excluded from search", and the withdrawn state is excluded — so `find()`, `all_ids()` and `names()` would all have looked straight past a withdrawn course, and the next synchronisation would have made a second copy of it rather than putting the first one back. They name the states they mean now. The string extractor also learned `_n_noop()`, which is how a status count is registered, and which it had been walking past.
- **A trainer's photograph was fetched again and again: 2 116 pictures of twenty-two people, 309 of one of them.** The guard was there and asked the wrong question. It compared the incoming address with the last one fetched — and iSport keeps more than one trainer record under the same name, eleven of this gym's twenty-two names having two or three, each with a photograph of its own. A course names whichever record it was booked against, so walking a hundred courses made the address flip back and forth, and every flip was a download and a new attachment. The question is now "is this an address I have ever fetched", which the flipping cannot defeat; a photograph genuinely new to iSport still arrives, because its address is one nobody has seen. Two guards sit behind that: an attachment already made from an address is reused rather than made again, and no trainer is fetched more than once in a single run whatever the courses say. Measured after the fix: three synchronisations in a row, nothing downloaded, and the picture on each trainer's page stops changing hands between two copies of itself.
- `wp cscs trainers tidy [--dry-run]` clears out what the old behaviour left behind. It keeps the picture the page actually shows and anything used as a featured image, notes the addresses of the copies it removes so the next synchronisation does not fetch them straight back, and deletes the rest. On this gym's site: 2 116 attachments down to 115, every trainer keeping their photograph, and the two without one having none in iSport either.
- **The course dropdown beside the editor hung over the edge of the screen.** `width: 100%` looked like the answer and is half of one: a select is as wide as its longest option, and in a column that sizes itself to its contents — which is what a meta box beside the editor is — the percentage resolves against a width the select has just pushed out. Measured on this gym's courses, 370 pixels of control in a 250 pixel column. The option text is cut to twenty-six characters, which is enough because a course title opens with the number that identifies it, and the whole title is on the option as a tooltip; the open list is drawn at whatever width it needs. 370 pixels became 227.
- **The Fetch description button said nothing whatever it did.** It redirected with the outcome in the URL and nothing rendered it, so a kind whose courses carry no description in iSport looked exactly like a broken button — which is how it was reported. It now says which of the two happened, and where the description would have to be written for there to be one.

### Security
- **A trainer's photograph was fetched from whatever address the response carried.** Everywhere else the plugin talks only to the host an administrator configured — that is a promise the security checklist makes in so many words — and here a field in somebody else's JSON decided what this server would ask for, with the answer going into the media library. The address must now match the configured base on scheme, host and port before anything is downloaded. Found by reading the checklist against the code rather than by anything going wrong, which is the argument for reading it.
- The checklist's own "No file uploads" line had quietly stopped being true when the settings import arrived. It now says what the import does and what bounds it: administrators only, nonce-checked, refused above 256 KB, read as JSON and never written to the filesystem, refused outright unless it carries the plugin's own format marker, and every value in it passed through the same validating setter the form uses.

### Added
- **Pause synchronisation**, on the overview screen beside Synchronise now. The scheduled jobs are cleared rather than left in place and skipped, because a paused plugin still holding four cron entries reads as a running one to anyone looking at the schedule. Synchronising by hand goes on working, which is the point: it takes the automatic traffic out of the way while a term is being set up, without going offline. `wp cscs sync pause on|off` says the same thing from a terminal, and `wp cscs sync pause` reports which it is.
- **A progress indicator on the buttons that take time.** Synchronising reaches the remote system several times and can take most of a minute; the page simply sat there, and the honest reading of a page that sits there is that the button did nothing, so people pressed it again.
- **Fetch every missing description**, for the twenty-six kind pages at once rather than one at a time. It fills in only the pages with nothing written on them — a page somebody has written on is a page nobody asked this to touch — and reports how many it filled, how many it left, and how many have nothing in iSport to take. `wp cscs sync descriptions [--overwrite]`.
- **Settings export and import.** Twenty-odd values, several of them lists of activity names that took an afternoon to get right; retyping them on the staging copy is how they end up subtly different from the ones that were tested. Import is not a restore: every value goes through the same validating setter the screen and the command line use, and a value the plugin would refuse to store is counted and reported rather than written — so a file from a stranger can do nothing that could not be typed into the form.
- **The list of kinds of course shows the description and the number of courses**, and both can be switched off under Screen Options — which needs nothing but registering them as columns, because WordPress lists every column of a list table there and remembers each person's choice separately. Which kinds are still empty, and which somebody has rewritten, is the one thing about kind pages worth checking across all of them at once, and opening twenty-six pages to find out is not checking.

## [1.0.0-alpha.1] - 2026-08-29

### Added
- A course page says **Day** and **Time** where it used to say **When**. One field holding "Mon 16:00, Wed 17:00" is two facts in the one form nobody can read a timetable out of; as two fields whose lines run in step, the first day belongs to the first time and the reader never has to guess. The classes table has learned to report the end of a slot as well as its start, which it knew all along and was never asked.
- **Trainers** are a post type of their own. iSport has a name and, at best, a photograph; the qualifications, the interests, the sentence that makes somebody a person and the motto exist nowhere in the remote system and never will. So a trainer is a post: the synchronisation keeps the name and the photograph current and touches nothing else, permanently. Qualifications and interests are lists because that is what they are — a person holds three certificates, not a paragraph mentioning three.
- Pairing is by the same normalised name the whole plugin already matches on, because it is the only identifier both sides have. The `cscs_trainer` taxonomy stays exactly as it was: it is what display sets filter by and what several hundred courses are tagged with, and replacing a working filter for a tidiness nobody can see would be paying in broken configuration. A course links to its trainer; a trainer's page lists every course they run. `wp cscs trainers backfill` builds the pages from courses already stored, rather than making anybody wait for tomorrow's synchronisation.
- A trainer's photograph is fetched on the server and stored in the media library, so a visitor's browser never asks iSport for anything — hot-linking would have told the remote system who is reading the site, which is precisely what this plugin promises not to do. A featured image set by hand always wins over it; that is the point of being able to replace it.
- **A named block for every field a page is built out of** — Price, Day, Time, Runs, Classes, Room, Trainer, Places left, the sign-up button, the timetable, the make-up classes, and for a trainer the photograph, qualifications, interests, motto and courses. The tempting economy is one block called "Field" with a dropdown on it, and the trouble is the first thing anybody does: they open the inserter, type "price", and find nothing. One catalogue knows what each field means, and the blocks, the Divi modules and the plugin's own templates are generated from it — so a field added there appears in three editors at once and cannot say three different things.
- Each of them carries everything WordPress's block supports offer — colour, background, gradients, typography, spacing, borders, shadow, sticky position, wide and full alignment — **and two typography sets of its own, one for the heading and one for the value**. Block supports style a block as a whole, and this block is two things: "Price" wants to be small and quiet, "4 160 Kč" wants to be large. Everything a browser will be handed is checked against a pattern or a list first; an attribute arrives from a saved post, and "it came from our own editor" is not a claim about safety.
- Left alone, a field block shows whichever course or trainer the page is about, which is what a template in a theme builder needs and what makes one design serve every course. A field with nothing to say leaves rather than printing a heading over a blank space, exactly as an empty column is dropped from a listing.
- Animations run when a field first comes into view rather than on load, through an `IntersectionObserver`, and never for a visitor who has asked their system to reduce motion — that request is often a medical one, not a preference to be weighed against a design. Nothing is hidden by the markup: an element is only made invisible once something is certainly going to bring it back, so a page whose JavaScript failed shows everything.
- **A Divi 5 module for every one of those fields**, from the same catalogue, with Divi's own design groups — and three sets of them rather than one: the module, the heading, and the value. A builder that can only style a "price module" as a whole leaves you writing CSS the moment the word and the number need to differ, which is immediately. The two typography groups are declared with names of their own; left to Divi's defaults both come out called "Module Text", and a panel with two identically named groups in it is a panel nobody can use.
- **Every one of the plugin's Divi modules lives in one folder called "iSport"**, and each carries an icon of its own. Divi's module list is alphabetical and long: twenty-seven modules spread through it are not a set anybody can find, and Price between Portfolio and Pricing Tables is not recognisably ours. This is the shelf WooCommerce's modules sit on, under the plugin's own name — a `folder` key on each module and a folder registered in the builder. The icons are Divi's own; there is no public way to add one to its set, and a picture is not worth reaching into a theme's internals for.
- **A trainer's table says the day and the time in two columns**, the way the course's own page does. "Po 15:30" is two facts in the one shape nobody can read a timetable out of, and a course that meets twice a week had both crammed into one cell. The two columns run in step — the first day belongs to the first time — and both are offered to display sets as well, beside the combined column, which stays exactly as it is so that no set anybody has already saved changes under them.
- **A table can be designed part by part** — the heading row, the cells, the links inside them, the rule between them, the banding behind them, and the width and alignment of every column. A course's timetable, its make-up classes and a trainer's courses each draw a table, and until now the only thing a designer could reach was the heading above it. In Divi each part is a group of its own, in the language the rest of the builder speaks; in a block they are panels, and the block writes the rules itself, scoped to a class named after the settings — a table nobody has designed writes nothing at all.
- **Who a course is for and at what level** — "dívky", "mix", "mírně pokročilí" — as two more facts on a course page, two more columns in a listing, and a block and a Divi module each. iSport publishes neither: there is no field for either one anywhere in the two endpoints, and the site this replaces reads both out of the course's name, which is where they are read from here. The vocabulary is a fixed list matched whole word against the name with its accents and its case flattened, so "mix" is not found inside "mixáž" and a name typed without diacritics reads like one with them; "mírně pokročilí" is looked for before "pokročilí", or every improver is filed as advanced. Of the 113 courses on this site 104 say something and the rest say nothing — and a course whose name says nothing is given nothing, because a fact invented for a page is worse than a fact missing from it.
- A reading can be overruled on the course itself, and the choice survives every synchronisation: it goes on the same locked-fields list that already protects a description somebody wrote. `wp cscs sync audience [--dry-run]` re-reads the whole catalogue, and two filters — `cscs_course_gender_terms` and `cscs_course_level_terms` — open the vocabulary, because a gym that words things differently should not have to patch a plugin to say so.
- The level agrees with the group it belongs to, because Czech makes it: a course for girls is one of "začátečnice" where a mixed one is of "začátečníci". Both are "Beginners" in English, so the two are told apart by a gettext context rather than by their text — and the string extractor and the catalogue builder now carry contexts through, which they silently did not. They also no longer emit a string twice when it is both written in PHP and listed by hand for a JavaScript file; a catalogue that defines one string twice is one gettext will not read.
- **A course is filed under the kind of course it is** — "Gymnastika", "Jojo přípravka", "Lezení", "Gymnastika pro radost" — read from its own name. This is the thing a page's card is made of, and nothing in the remote data holds it: iSport does send an activity, but it sends the whole course name as one, so the activity taxonomy held one term per course and grouped exactly nothing. What the names do have is a shape — number, kind, age, group, level, term — so the kind is what stands before the first thing that is not the kind. The 113 live courses fall into 25 kinds, which are the 25 cards the website publishes. A display set ticks one and the card is built; a kind read wrongly is corrected on the course and locked like anything else a person has corrected.
- **The synchronisation was not running, and nothing said so.** Two of the four scheduled jobs run on intervals the plugin declares itself, and `wp_schedule_event()` refuses a recurrence WordPress does not know at the moment it is called — which on the activation request it does not, because a plugin being activated is not yet in the list the `cron_schedules` filter is added from. So the two daily jobs were scheduled and the two that matter were silently not: courses stopped being fetched, the pages went on rendering, and the places free stayed at whatever they were when anything last ran. On this gym's site 44 of the 113 courses were out of date by the time somebody noticed a course offering six places that iSport was offering five of. The jobs are now checked on every load rather than only at activation, the intervals are registered before anything is scheduled, a job whose interval is somehow still unknown falls back to hourly rather than to nothing, and changing an interval reschedules the job instead of waiting for the plugin to be switched off and on. **iSport → Overview** lists all four with when each runs next, so a job that has stopped says so on a screen rather than only in the numbers.
- **Saving a course no longer takes its age, group and level away.** The editing screen offers "as the name says", and choosing it deletes the stored value — which is right, an empty string is a value and would be shown — but nothing then read the name, so the fact was simply gone until the next synchronisation. Two of the 113 courses were sitting like that: course 28 knew nothing about being for girls, for beginners, or for six to nine year olds, on every table it appeared in. The name is read again as the screen is saved, for everything left unlocked.
- **A kind's page says which of its courses it is about, and a template made once serves them all.** The gym publishes *Gymnastika* as one card and wants the girls' hours and the boys' as two, and refiling twenty-two courses under a kind invented to hold half of them says nothing the courses do not already say. The question — who the course is for, at what level, an age floor and ceiling, an order, a limit — is therefore asked on the **kind's page**, in a *Which courses* panel, and not in the design: a theme builder template is one design for every page of a type, so an answer given there is given for all of them, "girls" on the page for the boys. A page can also name the kind it is about outright, because a page called "Gymnastika dívky" pairs with no kind by its name. One template, three pages, three timetables: 22 rows, 18 and 2 — and the prices table narrows with them, so the boys' page prices the boys' courses. **Copy** in the list of kind pages makes the second page from the first, description, picture and all.
- The same settings exist on the block and the Divi module, for the other case: a module dropped on one particular page that wants something else. What a person filled in there wins; what they left alone does not, which took some care — every module sends every setting whether it was touched or not, so a direction of "ascending" with nothing to sort by had to be told from a decision, or one design would have shouted its own defaults over all twenty-six pages.
- **A wide table scrolls inside its own frame instead of off the page.** Eight columns are wider than the content column of most themes, and the last of them — the sign-up button — was simply not on the screen. It is a region of its own now, with a tab stop, because something a reader has to scroll is something a reader has to be able to reach without a mouse.
- **Folded onto a telephone, a cell with nothing in it takes its heading with it.** Every row becomes a card there and every cell grows a label, so a course that says nothing about its level was showing "Level" over a blank line. The rule that was meant to prevent this could never fire: `td:empty` does not match a cell containing a newline, and the markup puts one there.
- Both of those were found by looking at a screenshot, not by reading the code — which is the argument for the screenshots being part of the work rather than a thing done afterwards for the listing page.
- **The official Plugin Check passes with nothing to say** — no errors and no warnings, in every category including the repository one, run against the WordPress.org build on a clean WordPress with no other plugin and no Divi. Twenty-nine findings were fixed to get there. The interesting ones: the direct-access guard sat below fifty `use` statements in sixty-one files, which is below the point anything checks; every variable a template reads is now prefixed, because a template is included at file scope and a bare `$listing` there cannot be told from a global; and `load_plugin_textdomain()` is gone, since WordPress has loaded a plugin's own translations by itself since 6.7 — which is now the version the plugin asks for. The rest were sniffs the plugin had already answered for WordPress's rule set and not for Plugin Check's, so each ignore now names both and says why.
- **The plugin was installed and exercised on a clean WordPress with `WP_DEBUG` on**: thirty-one blocks, three post types, three taxonomies, the role, both tables and all four scheduled jobs registered on activation; the shortcode rendered; the front page answered; and `debug.log` was never created, because nothing wrote to it. Then the same code on the development site with Divi 5.11: 113 rows, every block and module drawn, no notice.
- Renaming those template variables broke one caller that set the old name, and the with-Divi run is what found it — which is the argument for running both. It is fixed, and the redirect rule the security audit added now has tests of its own: another host, another scheme, another port and a protocol-relative address are all refused; a trailing slash on the same host is followed.
- **A listing of 113 courses was 119 database queries. It is now 7.** One of them fetched the rooms of one course, and it ran once per row — `wp_get_object_terms()` asks the database every time, where `get_the_terms()` reads a cache. The cache is now filled for the whole page in a single query before the first row is built, and the same is done on a kind's page and a trainer's, where reading twenty-two courses by id had been twenty-two more. Rendering that listing went from 191 to 51 milliseconds; a kind's timetable from 37 queries to 17. Nothing on the front end makes an outbound request, which is checked rather than believed.
- **A page that changes under a reader who cannot see it now says so.** Pressing "next week" replaces the table with no movement of focus and no navigation, so a screen reader announced nothing at all — WCAG 2.1's status-message rule, and simply what a person would say if they were doing the pressing for you. The listing carries a quiet live region that reads out the week, the page and how many rows arrived. Every table gained a name — its heading where it has one — because a table with none is "table, five columns" and a page may carry three. And the plugin draws its own focus outline in the colour of the text: the theme usually draws one, but a link inside a table whose colours somebody has designed can end up outlined in what is behind it.
- **A price is written the way the site's language writes numbers**, and the currency is a translatable string rather than "Kč" in the source. A course's own page was printing "1. 9. 2026" under a site set to write dates some other way; it uses the site's date format now, as the listings already did. The catalogue is 575 strings with nothing left untranslated, and every translation call was checked by parsing the source rather than by grepping it: no concatenation inside a translation function, no missing text domain, no placeholder without a note for whoever translates it.
- **The design lock held on one block of sixty-one.** The site owner's first requirement was that whoever maintains the courses may say which listing appears and nothing about how it looks, enforced on the server rather than by hiding a panel. It was — on `cscs/divi-display`, the one module that existed when the guard was written. Every field block and field module added since was unguarded, so a site manager without `cscs_manage_design` could recolour any table, restyle any heading and write custom CSS on any of them, and the save would keep it. The guard now visits every block whose name begins `cscs/`, with the content keys each kind actually offers — for a Divi module that is Divi's own Content panel, for a block its Settings tab, so the server and the builder cannot disagree about what a person may change. Blocks are counted per name, so inserting one kind no longer shifts another kind's design by one.
- **A redirect out of the booking system is no longer followed.** The checklist said requests go only to the configured host and a redirect elsewhere is refused; WordPress was being asked to follow two hops to anywhere. An open redirect on the booking system would have been an open redirect out of this site's server. One redirect is now followed by hand, and only when the scheme, host and port are the ones that were asked for.
- Fourteen files had no direct-access guard; the public listing route would write any address given to it into the links of the page it returned; the preview route drew a course nobody had published for anyone with `edit_posts`; and `uninstall.php`, written before kinds existed, left the kind pages and every term of the plugin's taxonomies behind. All four are fixed, and `docs/SECURITY-CHECKLIST.md` records the audit control by control, including what was checked and found sound.
- **All thirty-one blocks stand under one heading called "iSport"**, the way the Divi modules already do and the way WooCommerce's blocks do. Scattered through "Widgets" they were not a set anybody could find, and half of them are called things like *Price* and *Name* — a name that means nothing beside the fifty blocks WordPress and a theme already offer. The category is put after the ones WordPress ships and before whatever other plugins have added, rather than at the end, which is only ever wherever the last plugin to be activated left it.
- **The words written about a kind are a block and a Divi module too.** *Course description* and *Description from iSport* both ask a course, so on a kind's page they had nothing to answer with — and a theme builder template, which is where a global page for all twenty-five kinds gets built, has nowhere to type the text by hand. **Kind description** shows what is on the page: the description fetched from a course, or whatever somebody wrote over it, with the same designable bullets every other text field has.
- **The kind modules opened in Divi's builder without an error.** Every field module offers a list of the posts it may be pointed at, and that list was built from a hand-written map of contexts which nobody extended when the kinds arrived — so a kind module handed the builder a select whose options were null, and Divi answered "this content cannot be displayed" in the settings panel while the page itself rendered perfectly and said nothing was wrong. Both the modules and the blocks now ask the catalogue which posts a context lives in, so there is no second list to fall behind, and a test says every context still has an answer.
- **A kind's page starts with the description its courses share**, so a Divi template for kinds has something to show on all twenty-five of them without anybody typing. Which description is a real question — eleven of the twenty-five kinds hold more than one wording and *Gymnastika* holds five across twenty-two courses — so the one the most courses agree on is taken, which for Gymnastika is the text eighteen of them share. It is written once, when there is nothing on the page, and never again: a page somebody has written on is a page nothing else touches. Beside the editor there is now a **Description from a course** panel to fetch it again from any single course of that kind, which is the answer for the eleven and for the day a particular course words it better.
- **What a kind costs is a table of two columns.** An hour of gymnastics and an hour and a half of it are different courses at different money — on this site nearly every kind has two — so the **Prices of this kind** block and module answer with a table headed *Délka* and *Cena* and one row per pair actually on offer: 60 minut / 4 160 Kč, 90 minut / 5 160 Kč. No more rows than there are distinct pairs, however many courses share one: twenty-two courses of Gymnastika make two lines, not twenty-two, and across the twenty-five live kinds not one repeats a row. It is a listing like every other table here, built from one representative course per pair, so it words itself, folds on a telephone and is designed exactly as the rest are. The table of a kind's courses carries neither: two numbers repeated down twenty-two rows say the same thing twenty-two times and narrow the columns somebody came to read. Length is a column any listing can use, worked out from the classes the course actually runs.
- **A kind of course is a page of its own.** The website this replaces publishes one per kind — a heading, a paragraph about what the training is, a photograph, and the timetable of every course of that kind — and a taxonomy term can hold none of that: it has a name and a plain-text box. So a kind is both, exactly as a trainer is: the `cscs_kind` taxonomy keeps the grouping and files the courses, and a `cscs_kind_page` post carries what somebody writes. The two are tied by the same normalised name the rest of the plugin matches on, which means a page retitled *Gymnastika pro děti* still belongs to the kind *Gymnastika*. Pages appear under **iSport → Druhy kurzů**, at `/druh/…`, and are made the moment a course is filed under a kind — an editor finds them waiting rather than having to know they must be created first.
- **Courses of this kind** is a block and a Divi module: the timetable of everything filed under the kind whose page it stands on, with the columns a visitor reads — day, time, age, gender, level, places left and the booking button — and the full table design behind it. It is the one part of such a page nobody can write by hand, because it changes every term.
- **A list from iSport is one level of bullets, and the bullets can be designed.** The booking system's editor wraps a list inside a list — in 24 of this gym's 113 courses — so a page showed two levels of marks where one was meant, and no stylesheet could undo it because the second level was really in the markup. The nesting is flattened on the way out: sub-items join the list above them, an item left with nothing is dropped, and a list that was already flat is handed back untouched. Every text field that can hold a list now also carries the marks themselves as something to design — what they are, their colour, the indent and the space between items — in the block's **Styles** tab and in Divi's design panel as *Bullet item* and *Bullet mark*.
- The block's panels are sorted the way WordPress sorts its own: **Settings** holds what the block shows (which course, what to say when there is nothing), **Styles** holds how it looks. They were all in Settings, which is where a designer looks last.
- **The description iSport holds for a course is a block and a Divi module of its own**, beside the one showing what was written in WordPress. They are two texts, not two sources for one: the gym writes one for its own website and the booking system holds the other, and a page should be able to show either, both or neither. This was worth finding — of the 113 live courses, *none* has a word written in WordPress and 111 have a description in iSport, so the field a page had was the empty one and the full one was unreachable.
- A course's own page, which draws itself when no builder has been used, shows the iSport description where nobody has written anything. Anything written in WordPress wins the moment it exists. The remote text arrives as markup, usually opening with a stray `<br>` that is nothing but a gap at the top of a page, so that is trimmed and the rest goes through the same filter as any post content.
- A course has two names, and where they differ it is the activity that says which card it belongs on. Course 25 is called "Gymnastika 4-6 let dívky pokročilé" and its activity is "Jojo přípravka 4-6 let dívky pokročilé"; the website this replaces publishes it under Jojo přípravka. So the kind is read from the activity name and falls back to the course's own — for 99 of the 113 courses the two are the same string, and the fourteen that differ are mostly a stray space. Reading the course name alone put one row on a card it did not belong on, which is exactly the kind of error nobody finds by reading code.
- **Several courses under one name.** The site this replaces publishes a card called "Gymnastika dívky" — one heading, one table, nineteen courses that share nothing in the data except that a person decided they belong together. A display set could only ever answer with filters, so it could not build that card. It now also carries a list of courses named by hand, a list of courses to leave out, and filters for gender, level and age. The filters gather the obvious ones, the named courses are added, the excluded ones are taken away, and the result goes to the query as a list of ids — so ordering and paging still happen in the database and a set written before any of this queries exactly as it did. A set that names courses and filters by nothing means those courses and no others, which is the only reading that is not a trap.
- **The age a course is for** is the last of the three facts iSport does not have a field for, and the one the old site puts in its own column. It is read from the name in the three shapes the catalogue writes: "9-11 let" is a range, "od 10 let" is a floor with no ceiling, "4 roky" is one age. The unit is what tells an age from the course's own number — "101-Lezení od 10 let" has two numbers in it and one of them is an age — and halves survive, because the gym runs courses for two-and-a-half-year-olds and rounding one down would put a toddler in the wrong room. 106 of the 113 live courses say an age; the ones that do not are the adults' classes, which never said one. It is a column, a fact on the course page, a block and a Divi module like everything else, and it can be overruled by hand on the course, where the two ends lock together: half a fact set by hand and half read from the name is a state with no screen to explain it on.
- The hand-picked lists stay as the escape hatch they were meant to be rather than the way a card is normally built: a filter that is right about forty courses and wrong about one is worth correcting, not replacing with a list of forty-one written out.
- Age filtering is overlap rather than containment — a set for 7 to 9 keeps the course for 6 to 8, because a seven-year-old could join it — and a course whose age nobody knows is left out of an age-filtered set rather than guessed into it.
- The modules' metadata is generated by `php tools/build-divi-modules.php` from the same field catalogue and committed, because Divi reads a module from a directory holding `module.json` and twenty-three directories of near-identical JSON is not something to maintain by hand. The price of a generated file in a repository is that somebody adds a field, forgets to run the generator, and the module is simply missing with nothing to say so — so the test suite compares the two.

A real course still wins over the list.

Course lessons are tagged "Kurz" and rentals "Pronájem haly", so the record says outright what it is; the old heuristic misfiled drop-in classes and make-up lessons, which have both a trainer and a price and belong to no course by design. The tag identifier differs between installations, so the label is compared, and the list is filterable through `cscs_course_lesson_tags`.

The column is now `NOT NULL DEFAULT 0` and zero means "no course", asserted in a test rather than assumed.

The curated list of activity names is still asked first: in this installation the tags do not separate the cases, since an outside lecturer's course carries "Pronájem haly" in one place and "Open lekce" in another, and the gym rents halls to the public under the same label. A tag that means two things cannot overrule a list that means one.

Only when exactly one course fits: a wrong guess shown beside the wrong course is worse than no guess. Nothing is written on the strength of it; a person still decides.

The link deliberately hangs off the single occurrence and not its name: the gym reuses one name for the make-up slot of whichever course needs one, so two occurrences spelled identically can belong to two different courses, and a name-wide link would be right once and wrong the rest of the time. `wp cscs makeup list [--unlinked]` lists the occurrences with their date, time, room and trainer; `wp cscs makeup link <term-id> <course-id>` records one.

The module also ships `module-default-render-attributes.json` now — Divi writes a chosen value into the structure the defaults describe, and without one there is nothing to write into. ### Fixed
- **The plugin's stylesheet never reached a Divi theme builder template.** It is enqueued where something renders — the shortcode, the block, the plugin's own course and trainer templates — and a theme builder layout is none of those: it replaces the template, so nothing asked for the file. Every table on a trainer's page was therefore drawn without its rule, its spacing or the fold that turns it into one card per row on a telephone, and nothing said so. Both Divi modules now ask for it when they render.
- The **picture panel never appeared in a block**. The catalogue the editor script reads had every field's name, kind and heading in it and not the one flag that says "this field is a picture", so the panel that chooses the size, the alternative text and the link was skipped on the two fields that have one. It was written and registered and reachable by nothing.
- **Design settings now take effect in Divi's builder while you are in it**, rather than only after the page is saved. Nothing about the modules was wrong on the page — every setting was stored and rendered — but the canvas never changed, which makes a builder you cannot design in. Two things were missing, and both fail without a word. Divi decides from an attribute's `elementType` which style components it gets, and an attribute that does not declare one gets none; the heading, the value and the picture now say what kind of element they are, the way Divi's own modules do. And a module's CSS has to be written with its order class already set on it, or the rules come out beginning with a space and belong to nothing; the modules now set their classes before asking for their styles, and render them inside the module the way Divi's own do. Verified in an ordinary page and in a theme builder template, on typography and on a picture's corners.
- The **Photograph** and **Course picture** modules behave like a picture rather than like a price. A picture is a different shape from a number, and giving both the same panel is what left them without the settings anybody would look for: which of WordPress's sizes to serve, what the picture says to a reader who cannot see it, and whether it is a link — to its own page, to the full-size file, or anywhere you name. The border, the corners, the shadow and the framing now sit on the `img` itself, which is where Divi's own Image module puts them and why rounding a photograph's corners on the module did nothing.
- Declaring those settings was only half of it. Without `styleProps` Divi knows which element a field belongs to and still has nowhere to write its CSS, so every one of them accepted a value and did nothing; the module now emits the picture's styles alongside the heading's and the value's. A setting that is offered and quietly ignored is worse than one that is not offered at all.
- The content panel was still in English while everything around it was translated. The fields are written in English in the generated module files and were handed to the builder that way; their wording is the site's business, so it is now translated at runtime like the module titles.
- A field with nothing to say left a gap behind it. It printed nothing, correctly, but the Divi module wrapper around it stayed — and a Divi column is a flex container with a gap between its children, so a module of no height still cost one gap. On a trainer who had filled in no interests, that was a hole between two sections with nothing on the page to explain it. An empty field now leaves the page entirely, wrapper and all; the listing module does the same.
- A field in a Divi theme builder template said the page was neither a course nor a trainer, on a page that plainly was one. The module asked `get_post()`, and while a theme builder layout renders, the global post **is the layout** — so every field on the one kind of page the option exists for reported the one thing that could not be true. It now asks `get_queried_object()`, which is what the visitor asked for and does not move.
- While a theme builder template is being designed there is no particular course to show, so every field previewed as "this page is neither" — true, and useless, since a page whose every element refuses to appear cannot be laid out. The builder is now shown a real record, the way Divi shows sample text in its own dynamic modules. Only ever in the editor: the fallback is reached in a REST request from somebody who may edit posts, and a visitor's page is not a REST request.
- The builder said "choose one in the module settings" where a field simply had nothing to print, which sent people looking for a setting to change. It now says the field is empty for this record and will not appear on the page — which is what is happening. The two builder strings are handed over with the module metadata rather than fetched through `wp.i18n`: the Visual Builder loads its packages through Divi's own manager, and a handle WordPress never registered is one `wp_set_script_translations` cannot reach, so they stayed English while everything around them was translated.
- Structured data was never printed on a course page. `wp_head` runs before the loop, and the guard asked `in_the_loop()`, which is always false there — the one kind of bug that leaves no trace on the page it is missing from.
- A post type added in an update brings URLs with it, and those only work once the rewrite rules have been rebuilt. Activation was the obvious moment and the wrong one — an update is not an activation, and every trainer page on an already-running site would have answered 404 with nothing to say why. The rules are now rebuilt once per version that adds a URL, the same way the schema and the capabilities are.
- Continuous integration: the first run failed every job. `npm ci` had no lock file to install from and there was no JavaScript to build, `phpunit/phpunit` and `phpstan/phpstan` were missing from the development requirements, and PHPStan was pointed at a `templates` directory that does not exist yet.
- Coding standards: every violation reported by PHP_CodeSniffer against the `WordPress`, `WordPress-Docs` and `PHPCompatibilityWP` rulesets, verified locally against the same tool versions the pipeline resolves.
- Static analysis: WP-CLI stubs and the WordPress time constants are now declared, so PHPStan resolves every symbol at level 6.
- The failure circuit no longer punishes a repair. Changing a setting that affects requests — the base URL, a timeout, the retry or ceiling values — closes the circuit and drops the cached responses, and `wp cscs api reset` does the same on demand. Previously, correcting a bad base URL meant being told for the next half hour that requests were paused.
- The client no longer refuses a response because of its `Content-Type`. The iSport endpoints are hand-written PHP that announces JSON as `text/html`, so the check rejected the live system while accepting nothing extra: the real protection was always that the body decodes to an array. A body opening with a tag is now reported as an error page rather than as a JSON syntax error, and a leading byte order mark no longer defeats decoding.
- `readme.txt` no longer promises screenshots that are not in the repository, and declares the current WordPress release.
- `yoast/phpunit-polyfills` removed: it caps PHPUnit at 9 and is only needed by the WordPress core test suite, which this plugin does not use.
- Plugin Check now runs against a build of the WordPress.org artefact rather than the repository, with the slug supplied explicitly, so it sees what would actually be submitted instead of the development tree.
- The redundant PHP version guard is gone. WordPress enforces `Requires PHP` itself and refuses to activate a plugin the server cannot run, so the check was an unreachable branch that static analysis rightly flagged.

### Changed
- A course's page lives at `/kurz/…` and a trainer's at `/trener/…`, not `/course/…` and `/trainer/…`. The plugin's own vocabulary stays English — that is for whoever maintains it — but an address is something a reader sees, and nothing a reader sees should be in a language the site is not written in. `cscs_course_rewrite_slug` and `cscs_trainer_rewrite_slug` filter them, and the rewrite rules rebuild themselves on the next request.

- The repository is renamed to match the plugin slug, so a checkout directory is never mistaken for the plugin name.
- Every quality gate now runs even when an earlier one fails, and each writes its output to the run summary. One push therefore reports every problem at once, and the results are readable from the run page without downloading an artifact.
