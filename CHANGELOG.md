# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- A course page says **Day** and **Time** where it used to say **When**. One field holding "Mon 16:00, Wed 17:00" is two facts in the one form nobody can read a timetable out of; as two fields whose lines run in step, the first day belongs to the first time and the reader never has to guess. The classes table has learned to report the end of a slot as well as its start, which it knew all along and was never asked.
- **Trainers** are a post type of their own. iSport has a name and, at best, a photograph; the qualifications, the interests, the sentence that makes somebody a person and the motto exist nowhere in the remote system and never will. So a trainer is a post: the synchronisation keeps the name and the photograph current and touches nothing else, permanently. Qualifications and interests are lists because that is what they are — a person holds three certificates, not a paragraph mentioning three.
- Pairing is by the same normalised name the whole plugin already matches on, because it is the only identifier both sides have. The `cscs_trainer` taxonomy stays exactly as it was: it is what display sets filter by and what several hundred courses are tagged with, and replacing a working filter for a tidiness nobody can see would be paying in broken configuration. A course links to its trainer; a trainer's page lists every course they run. `wp cscs trainers backfill` builds the pages from courses already stored, rather than making anybody wait for tomorrow's synchronisation.
- A trainer's photograph is fetched on the server and stored in the media library, so a visitor's browser never asks iSport for anything — hot-linking would have told the remote system who is reading the site, which is precisely what this plugin promises not to do. A featured image set by hand always wins over it; that is the point of being able to replace it.
- **A named block for every field a page is built out of** — Price, Day, Time, Runs, Classes, Room, Trainer, Places left, the sign-up button, the timetable, the make-up classes, and for a trainer the photograph, qualifications, interests, motto and courses. The tempting economy is one block called "Field" with a dropdown on it, and the trouble is the first thing anybody does: they open the inserter, type "price", and find nothing. One catalogue knows what each field means, and the blocks, the Divi modules and the plugin's own templates are generated from it — so a field added there appears in three editors at once and cannot say three different things.
- Each of them carries everything WordPress's block supports offer — colour, background, gradients, typography, spacing, borders, shadow, sticky position, wide and full alignment — **and two typography sets of its own, one for the heading and one for the value**. Block supports style a block as a whole, and this block is two things: "Price" wants to be small and quiet, "4 160 Kč" wants to be large. Everything a browser will be handed is checked against a pattern or a list first; an attribute arrives from a saved post, and "it came from our own editor" is not a claim about safety.
- Left alone, a field block shows whichever course or trainer the page is about, which is what a template in a theme builder needs and what makes one design serve every course. A field with nothing to say leaves rather than printing a heading over a blank space, exactly as an empty column is dropped from a listing.
- Animations run when a field first comes into view rather than on load, through an `IntersectionObserver`, and never for a visitor who has asked their system to reduce motion — that request is often a medical one, not a preference to be weighed against a design. Nothing is hidden by the markup: an element is only made invisible once something is certainly going to bring it back, so a page whose JavaScript failed shows everything.
- **A Divi 5 module for every one of those fields**, from the same catalogue, with Divi's own design groups — and three sets of them rather than one: the module, the heading, and the value. A builder that can only style a "price module" as a whole leaves you writing CSS the moment the word and the number need to differ, which is immediately. The two typography groups are declared with names of their own; left to Divi's defaults both come out called "Module Text", and a panel with two identically named groups in it is a panel nobody can use.
- **Every one of the plugin's Divi modules lives in one folder called "iSport"**, and each carries an icon of its own. Divi's module list is alphabetical and long: twenty-seven modules spread through it are not a set anybody can find, and Price between Portfolio and Pricing Tables is not recognisably ours. This is the shelf WooCommerce's modules sit on, under the plugin's own name — a `folder` key on each module and a folder registered in the builder. The icons are Divi's own; there is no public way to add one to its set, and a picture is not worth reaching into a theme's internals for.
- **A trainer's table says the day and the time in two columns**, the way the course's own page does. "Po 15:30" is two facts in the one shape nobody can read a timetable out of, and a course that meets twice a week had both crammed into one cell. The two columns run in step — the first day belongs to the first time — and both are offered to display sets as well, beside the combined column, which stays exactly as it is so that no set anybody has already saved changes under them.
- **A table can be designed part by part** — the heading row, the cells, the links inside them, the rule between them, the banding behind them, and the width and alignment of every column. A course's timetable, its make-up classes and a trainer's courses each draw a table, and until now the only thing a designer could reach was the heading above it. In Divi each part is a group of its own, in the language the rest of the builder speaks; in a block they are panels, and the block writes the rules itself, scoped to a class named after the settings — a table nobody has designed writes nothing at all.
- **Who a course is for and at what level** — "dívky", "mix", "mírně pokročilí" — as two more facts on a course page, two more columns in a listing, and a block and a Divi module each. iSport publishes neither: there is no field for either one anywhere in the two endpoints, and the site this replaces reads both out of the course's name, which is where they are read from here. The vocabulary is a fixed list matched whole word against the name with its accents and its case flattened, so "mix" is not found inside "mixáž" and a name typed without diacritics reads like one with them; "mírně pokročilí" is looked for before "pokročilí", or every improver is filed as advanced. Of the 113 courses on this site 104 say something and the rest say nothing — and a course whose name says nothing is given nothing, because a fact invented for a page is worse than a fact missing from it.
- A reading can be overruled on the course itself, and the choice survives every synchronisation: it goes on the same locked-fields list that already protects a description somebody wrote. `wp cscs sync audience [--dry-run]` re-reads the whole catalogue, and two filters — `cscs_course_gender_terms` and `cscs_course_level_terms` — open the vocabulary, because a gym that words things differently should not have to patch a plugin to say so.
- The level agrees with the group it belongs to, because Czech makes it: a course for girls is one of "začátečnice" where a mixed one is of "začátečníci". Both are "Beginners" in English, so the two are told apart by a gettext context rather than by their text — and the string extractor and the catalogue builder now carry contexts through, which they silently did not. They also no longer emit a string twice when it is both written in PHP and listed by hand for a JavaScript file; a catalogue that defines one string twice is one gettext will not read.
- **A course is filed under the kind of course it is** — "Gymnastika", "Jojo přípravka", "Lezení", "Gymnastika pro radost" — read from its own name. This is the thing a page's card is made of, and nothing in the remote data holds it: iSport does send an activity, but it sends the whole course name as one, so the activity taxonomy held one term per course and grouped exactly nothing. What the names do have is a shape — number, kind, age, group, level, term — so the kind is what stands before the first thing that is not the kind. The 113 live courses fall into 25 kinds, which are the 25 cards the website publishes. A display set ticks one and the card is built; a kind read wrongly is corrected on the course and locked like anything else a person has corrected.
- **A kind's page starts with the description its courses share**, so a Divi template for kinds has something to show on all twenty-five of them without anybody typing. Which description is a real question — eleven of the twenty-five kinds hold more than one wording and *Gymnastika* holds five across twenty-two courses — so the one the most courses agree on is taken, which for Gymnastika is the text eighteen of them share. It is written once, when there is nothing on the page, and never again: a page somebody has written on is a page nothing else touches. Beside the editor there is now a **Description from a course** panel to fetch it again from any single course of that kind, which is the answer for the eleven and for the day a particular course words it better.
- **What a kind costs is a table of two columns.** An hour of gymnastics and an hour and a half of it are different courses at different money — on this site nearly every kind has two — so the **Prices of this kind** block and module answer with a table headed *Délka* and *Cena* and one row per pair actually on offer: 60 minut / 4 160 Kč, 90 minut / 5 160 Kč. No more rows than there are distinct pairs, however many courses share one: twenty-two courses of Gymnastika make two lines, not twenty-two, and across the twenty-five live kinds not one repeats a row. It is a listing like every other table here, built from one representative course per pair, so it words itself, folds on a telephone and is designed exactly as the rest are. The table of a kind's courses gained **Length** and **Price** columns to match, so a visitor reading one row sees what that term costs rather than having to work out which price is theirs. Length is a column any listing can use, worked out from the classes the course actually runs.
- **A kind of course is a page of its own.** The website this replaces publishes one per kind — a heading, a paragraph about what the training is, a photograph, and the timetable of every course of that kind — and a taxonomy term can hold none of that: it has a name and a plain-text box. So a kind is both, exactly as a trainer is: the `cscs_kind` taxonomy keeps the grouping and files the courses, and a `cscs_kind_page` post carries what somebody writes. The two are tied by the same normalised name the rest of the plugin matches on, which means a page retitled *Gymnastika pro děti* still belongs to the kind *Gymnastika*. Pages appear under **iSport → Druhy kurzů**, at `/druh/…`, and are made the moment a course is filed under a kind — an editor finds them waiting rather than having to know they must be created first.
- **Courses of this kind** is a block and a Divi module: the timetable of everything filed under the kind whose page it stands on, with the columns a visitor reads — day, time, age, gender, level, places left and the booking button — and the full table design behind it. It is the one part of such a page nobody can write by hand, because it changes every term.
- **A list from iSport is one level of bullets, and the bullets can be designed.** The booking system's editor wraps a list inside a list — in 24 of this gym's 113 courses — so a page showed two levels of marks where one was meant, and no stylesheet could undo it because the second level was really in the markup. The nesting is flattened on the way out: sub-items join the list above them, an item left with nothing is dropped, and a list that was already flat is handed back untouched. Every text field that can hold a list now also carries the marks themselves as something to design — what they are, their colour, the indent and the space between items — in the block's **Styles** tab and in Divi's design panel as *Bullet item* and *Bullet mark*.
- The block's panels are sorted the way WordPress sorts its own: **Settings** holds what the block shows (which course, what to say when there is nothing), **Styles** holds how it looks. They were all in Settings, which is where a designer looks last.
- **The description iSport holds for a course is a block and a Divi module of its own**, beside the one showing what was written in WordPress. They are two texts, not two sources for one: the gym writes one for its own website and the booking system holds the other, and a page should be able to show either, both or neither. This was worth finding — of the 113 live courses, *none* has a word written in WordPress and 111 have a description in iSport, so the field a page had was the empty one and the full one was unreachable.
- A course's own page, which draws itself when no builder has been used, shows the iSport description where nobody has written anything. Anything written in WordPress wins the moment it exists. The remote text arrives as markup, usually opening with a stray `<br>` that is nothing but a gap at the top of a page, so that is trimmed and the rest goes through the same filter as any post content.
- A course has two names, and where they differ it is the activity that says which card it belongs on. Course 25 is called "Gymnastika 4-6 let dívky pokročilé" and its activity is "Jojo přípravka 4-6 let dívky pokročilé"; the website this replaces publishes it under Jojo přípravka. So the kind is read from the activity name and falls back to the course's own — for 99 of the 113 courses the two are the same string, and the fourteen that differ are mostly a stray space. Reading the course name alone put one row on a card it did not belong on, which is exactly the kind of error nobody finds by reading code.
- **Several courses under one name.** The site this replaces publishes a card called "Gymnastika dívky" — one heading, one table, nineteen courses that share nothing in the data except that a person decided they belong together. A display set could only ever answer with filters, so it could not build that card. It now also carries a list of courses named by hand, a list of courses to leave out, and filters for gender, level and age. The filters gather the obvious ones, the named courses are added, the excluded ones are taken away, and the result goes to the query as a list of ids — so ordering and paging still happen in the database and a set written before any of this queries exactly as it did. A set that names courses and filters by nothing means those courses and no others, which is the only reading that is not a trap.
- **The age a course is for** is the last of the three facts iSport does not have a field for, and the one the old site puts in its own column. It is read from the name in the three shapes the catalogue writes: "9-11 let" is a range, "od 10 let" is a floor with no ceiling, "4 roky" is one age. The unit is what tells an age from the course's own number — "101-Lezení od 10 let" has two numbers in it and one of them is an age — and halves survive, because the gym runs courses for two-and-a-half-year-olds and rounding one down would put a toddler in the wrong room. 106 of the 113 live courses say an age; the ones that do not are the adults' classes, which never said one. It is a column, a fact on the course page, a block and a Divi module like everything else, and it can be overruled by hand on the course, where the two ends lock together: half a fact set by hand and half read from the name is a state with no screen to explain it on.
- The hand-picked lists stay as the escape hatch they were meant to be rather than the way a card is normally built: a filter that is right about forty courses and wrong about one is worth correcting, not replacing with a list of forty-one written out.
- Age filtering is overlap rather than containment — a set for 7 to 9 keeps the course for 6 to 8, because a seven-year-old could join it — and a course whose age nobody knows is left out of an age-filtered set rather than guessed into it.
- The modules' metadata is generated by `php tools/build-divi-modules.php` from the same field catalogue and committed, because Divi reads a module from a directory holding `module.json` and twenty-three directories of near-identical JSON is not something to maintain by hand. The price of a generated file in a repository is that somebody adds a field, forgets to run the generator, and the module is simply missing with nothing to say so — so the test suite compares the two.
- Repository scaffolding: licence, documentation, coding standards, CI and release automation.
- Release checklist: the acceptance gate that must be fully satisfied before any submission to WordPress.org.
- Plugin bootstrap with its own PSR-4 autoloader, so the plugin ships without a Composer runtime dependency.
- API client for the iSport System endpoints, with bounded retries, a hard hourly request ceiling, a failure circuit breaker, and a cache that serves stale data rather than an empty page.
- Base URL validation that refuses plain http, credentials, non-standard ports, and any address in loopback, private, link-local or other reserved space.
- Payload mapper and type normalisation for both endpoints, including the course-to-class match key.
- WP-CLI commands `wp cscs api courses`, `wp cscs api lessons` and `wp cscs api doctor`.
- Unit tests with fixtures for normalisation, URL validation, mapping, every client guard, matching and the storage round trip.
- Data model: the `cscs_course` post type with room, trainer, activity and tag taxonomies, plus tables for class occurrences and the synchronisation log.
- Matching of class occurrences to courses on the normalised name and the term timestamp, with an accent-stripped fallback, permanent manual assignments, and a reported success rate that excludes hall rentals but not orphaned course lessons.
- Rooms of a course derived from the occurrences it actually runs in, rather than from the single room name the course record carries.
- Scheduled synchronisation: the course list, a near window of occurrences, a far window to the end of the term, and daily retention. Every job queries forward in time only.
- Retention: occurrences are kept for a configurable window behind today and then removed; courses are never deleted, only closed.
- WP-CLI: `wp cscs sync courses|lessons|rematch|unmatched|assign|retention`.
- `uninstall.php`, which removes data only when the administrator opted into that in the settings.
- Each stored occurrence records what it is — matched, external, not bookable, or unresolved — instead of a boolean that could not tell a hall rental from an activity that takes no bookings. A classifier comparing names as substrings is blunt enough that an over-broad entry would quietly reclassify things nobody meant it to, and until now nobody could look. `wp cscs sync list --status=not_bookable` shows exactly what it caught.
- The non-bookable list is actually declared among the defaults. It was added to the validation branch but not to `defaults()`, so the matcher was handed an empty list for a whole run while its own tests passed — they built the list by hand rather than reading the setting. Two tests now cover the wiring: one asserts the list has real content, and one asserts that every declared default is readable.
- Activities that occupy a slot in the timetable but take no bookings — courses run by outside lecturers, make-up lessons, individual training — are reported as their own category rather than as failures. They are tagged as courses, because that is what they are, and no course record will ever exist for them, so nothing in the data distinguishes them; the list is a setting, seeded with the activities Jojo Gym publishes as taking no registrations, and compared loosely so that "Zdravé cvičení" also covers "Zdravé cvičení s overbaly". A real course still wins over the list.
- A course is now indexed under both of its names. The API documents that `activity_name` "may be an alternative name" and the timetable uses either, so indexing only one lost every course that goes by two — six of them on the first live run.
- Whether an unmatched occurrence is a problem is decided by the tag the API already carries rather than inferred from the absence of a trainer and a price. Course lessons are tagged "Kurz" and rentals "Pronájem haly", so the record says outright what it is; the old heuristic misfiled drop-in classes and make-up lessons, which have both a trainer and a price and belong to no course by design. The tag identifier differs between installations, so the label is compared, and the list is filterable through `cscs_course_lesson_tags`.
- `wp cscs sync unmatched` shows each occurrence's tags, which is the first thing worth knowing about one.
- Unmatched occurrences were stored as `id_course = 0` while every query looked for `NULL`, so the synchronisation reported unresolved occurrences and the listing command found none — both reading the same rows. `$wpdb->prepare()` turns a null bound to `%d` into zero, which made the intended NULL unreachable. The column is now `NOT NULL DEFAULT 0` and zero means "no course", asserted in a test rather than assumed.
- A schema change now applies on the next request instead of waiting for the plugin to be deactivated and reactivated.
- The matching report groups unresolved occurrences by activity name. A weekly course that matched nothing produces one name rather than a dozen apparent problems, which is the difference between a number to worry about and a list to act on.
- Settings are written through a validating setter and seeded with their defaults on activation, so there is always something to read and edit. WP-CLI: `wp cscs settings list|get|set`.

- Tag handling is now a configurable map of label to category — `course`, `external_course`, `makeup` or `rental` — editable on the settings screen, one rule per line, instead of a hard-coded check for the word "Kurz". The curated list of activity names is still asked first: in this installation the tags do not separate the cases, since an outside lecturer's course carries "Pronájem haly" in one place and "Open lekce" in another, and the gym rents halls to the public under the same label. A tag that means two things cannot overrule a list that means one.
- `wp cscs makeup list` shows the course's name beside its id. An id on its own is unreadable, and an unreadable id is how a make-up lesson for four-year-olds ends up tied to a board games course for teenagers without anybody noticing.
- Make-up lessons are recognised by their own list of names, checked before the non-bookable list. They had been sitting on that list, so they were classified as something nobody books — true, but it meant the make-up category never triggered and `wp cscs makeup list` found nothing to show.
- Where a make-up lesson names its course — "Náhradní lekce 37-Gymnastika 9-11 let dívky" rather than today's "Náhradní lekce 4-6 let" — the course is read off the name and offered as a suggestion. Only when exactly one course fits: a wrong guess shown beside the wrong course is worse than no guess. Nothing is written on the strength of it; a person still decides.
- Make-up lessons can be tied to the course they stand in for. Nothing in the data says which course that is — the timetable calls one "Náhradní lekce 4-6 let I. pololetí" and twelve courses run for that age group — so a person records it, one occurrence at a time. The link deliberately hangs off the single occurrence and not its name: the gym reuses one name for the make-up slot of whichever course needs one, so two occurrences spelled identically can belong to two different courses, and a name-wide link would be right once and wrong the rest of the time. `wp cscs makeup list [--unlinked]` lists the occurrences with their date, time, room and trainer; `wp cscs makeup link <term-id> <course-id>` records one.
- Listings can be browsed: a week switcher on timetables, a room filter where a listing covers more than one, and paging where a set sets a page size. All of it is ordinary links with the choice in the address, so it works with JavaScript switched off; a small script then swaps the listing in place instead of reloading the page, and falls back to following the link whenever anything is unexpected. What a set decides and what a visitor chooses stay two separate objects, and a visitor can only narrow a listing to a room the set already covers.
- Every manual judgement can be taken back. A saved make-up assignment moves to the **Assigned** list and carries an *Undo this assignment* button; a manual assignment of a class gets a fourth list, **Assigned by hand**, which exists for exactly this reason — an assigned class is matched like any other and was, until now, unreachable from the screen the moment it was saved. A judgement nobody can find again is one nobody can correct, and a judgement that cannot be corrected is one people hesitate to make.
- Courses have a page of their own: the text and picture somebody wrote, the facts worth knowing already worded (with the empty ones left out), the lecturer's contact for the courses nobody books through iSport, the booking button under the same three rules as everywhere, the course's own upcoming classes, and the make-up classes tied to it — which belong on that page and nowhere else. It is added to the content rather than replacing the theme's template, because a course is a post and the theme already draws everything around it.
- A `Course` JSON-LD description in the head of every course page: the term as a course instance, the room as a place, and an offer only where there is a real price. Search engines are the second visitor a course page has.
- Every listing now renders through one shared `partials/table.php`, so the fold to one card per row is defined in a single place — the course page's tables and the listings behave identically on a telephone because they are the same file.
- A **Divi 5 module** with one content field: which display set. This is the arrangement the site owner asked for, finished: whoever maintains the courses opens the module, picks a set, and is done — and what that set shows is changed under iSport → Display sets, where every page using it follows without the builder being opened at all.
- The design settings beside it stay with whoever owns the design, and the rule is applied on the server. A save by somebody without `cscs_manage_design` keeps the design the module was stored with — not an empty design, and not a refused save, which would lose the content edit that was the point. Custom CSS counts as design. Hiding the panels would have been a courtesy: a builder is a browser application, and anything a browser decides can be undone in the browser.
- The module's one attribute is called `listing`, not `set`. Divi keeps attributes in seamless-immutable objects whose API includes `set` and `setIn`, so an attribute of that name collided with it: Divi dropped the attribute and refused every choice made in the field with `getIn(...).setIn is not a function`, while the field itself rendered perfectly and nothing looked wrong. The module also ships `module-default-render-attributes.json` now — Divi writes a chosen value into the structure the defaults describe, and without one there is nothing to write into. Pages saved under either earlier spelling are still read.
- The module's one field is declared as a setting rather than as the content of an element. Divi reserves `innerContent` for what an element itself contains; a setting declared there renders its field perfectly and then refuses every choice made in it, since the builder has nowhere to write the value. Pages saved under the older shape are still read.
- The builder component takes Divi's own copy of React from `window.vendor.React` and calls no hooks at all. WordPress's copy is a different one, and a component built from it may not call a hook — React keeps hook state per copy — which surfaced as the builder's "something went wrong" panel with nothing in it to explain itself, and left the module unable to accept the one setting it has.
- The builder's preview is fetched from the server (`GET /cscs/v1/preview`, editors only) rather than drawn again in React, because a module that renders itself twice — once in PHP for the page, once in JavaScript for the builder — holds two versions of its markup that quietly stop agreeing.
- The module needs no build step either: it reads the globals Divi already exposes, and its metadata comes from the same `module.json` the server registers, with this site's display sets put into the options.
- Without Divi none of this loads. Every hook fires only under Divi 5, and the classes naming Divi's own are read only from inside those hooks — a plugin that fatals without a commercial theme has no business being on WordPress.org, and the shortcode and the block have to keep working regardless.
- A column with nothing in it from top to bottom is left out of the listing. A set can ask for the booking button while the site has buttons switched off, or for the cancelled marker in a week when nothing was cancelled; rendered anyway, that is a heading over an empty column, which reads as a fault rather than as an answer of "none". The set is not changed — the column returns the moment there is anything to put in it. An empty listing keeps all its headings, since nothing can be concluded from a table with no rows.
- A **Courses and schedule** block for the editor, with one field: which display set. It renders on the server through the same renderer as the shortcode, so the editor's preview is the page rather than a drawing of it that drifts, and nothing is written into post content — a listing saved as markup would be a snapshot of a Tuesday. The editor script is plain JavaScript against the packages WordPress already loads: no build step, no compiled file in the repository, for a block that is one select box. Its strings are translated too.
- Capabilities are granted when they are missing rather than only at activation. A plugin is activated once, so a capability added in a later version reached nobody already running it — and since the whole admin menu hangs on `cscs_manage_content`, a site activated before that capability existed had no menu at all and nothing anywhere saying why. The check is one autoloaded option read, the same shape as the schema check, and it repairs the site on the next request. `wp cscs caps list|install` shows who holds what.
- Listings on the site at last: one renderer behind a shortcode, `[cscs_courses set="…"]` and `[cscs_schedule set="…"]`. A display set goes in, a table comes out, and the block and the builder module will come through the same code so that three ways of putting a listing on a page cannot drift into three different listings.
- Every table folds below a configurable width — each row becomes a card, each cell carrying its own heading down the left and the value beside it — which is the only shape a timetable of six columns can take on a telephone. The headings come from `data-label`, the `<thead>` is hidden from sight but left for screen readers, and the rule is generated rather than shipped because a media query takes a number and the width is a setting.
- Templates live in `templates/` and a theme may replace either of them by copying it to `course-schedule-connector/` or `jojo-isport/`. There is nothing left to decide by the time one runs — the cell text, the row classes, the wording for an empty listing and a full course are all worked out — so a rewritten template can change the markup without changing the rules.
- Prices are written the way the site owner asked: `1 960 Kč` with a separator that never breaks a line, no rounding, and two decimal places only when there are any. A price of nothing is not a price of zero: courses say "Free", classes say whatever the setting chose, and a stored `0` says the same rather than reading like a bargain.
- The booking button obeys the course, then the site-wide setting, then the facts — a full course or one iSport says takes no registrations shows no button whatever anybody set, because a button leading to a booking that cannot happen is worse than no button.
- Courses that exist only on this site. Jojo Gym takes neither bookings nor payments for an outside lecturer's class, so no course record will ever arrive from iSport, yet the class occupies a slot in the timetable and belongs on the website. One can now be made in a press from the unmatched screen — name, trainer, room and price copied across, the class tied to it permanently — or by hand like any other post. Rather than teach manual assignments, make-up links and every listing about a second kind of course, a hand-made course is given an id in a range the remote system will never reach, so it is a course like the others everywhere downstream. Synchronisation leaves it alone and never marks it as no longer offered: it was never in the remote list, and its absence from one means nothing. It is deliberately not indexed by name either — it carries no term list, so a name match would fail every timestamp check and turn correctly classified classes into failures.
- Admin: an **iSport → Rooms** screen. iSport names a room for the people who run the timetable — "Gymnastická hala 1 a veřejnost" — which is right there and unreadable in a table column on a phone, and renaming it there would disturb the gym's own work. The site keeps its own label, order, colour and a way to hide a room, all keyed by the remote id so that a rename in iSport does not throw the label away. The rooms offered are the ones the stored timetable actually uses, because no endpoint lists rooms and a stale list would offer rooms that no longer exist.
- Display sets: a named configuration of what a listing shows — which columns and in what order, custom labels, which rooms, trainers and activities, how far ahead, whether hall rentals belong in it, what to do with cancelled classes, sorting, page size, and the wording for the heading, the button, the empty state and a full course. This is what makes the arrangement the site owner asked for work: a page builder module offers a site manager one field, which set, so changing what a page lists never means opening the builder and the design stays where the design belongs. The rules live in a `DisplaySet` value object rather than in the screen that edits it — it normalises anything shaped roughly like a set, drops columns it does not recognise, holds numbers to a range and never throws, because a set that half-loads is worse than one that loads with a default in the field somebody mistyped. A set's id is a slug because a shortcode is written in terms of it, and it never changes afterwards: renaming a set must not empty a page. `wp cscs sets list|get`.
- Admin: a course carries the things iSport has nowhere to put — who to contact about it (name, e-mail, telephone, note), whether it shows the booking button regardless of the site-wide setting, and which synced fields a person has corrected and would rather keep. Anything ticked in **Fields synchronisation must not touch** survives every later run; capacity and occupancy are deliberately not among the choices, because freezing a number that changes by the hour turns a page into a lie. Beside the editor sits what iSport says about the course, read-only, with a link to the course over there.
- Admin: the course list shows state, booking button and contact as columns, and the booking button can be set on many courses at once. Turning it off for a season means doing it to dozens of courses, and one at a time is how that ends up half done.
- Admin: an **iSport → Unmatched lessons** screen listing what the matching could not place, alongside the classes it decided belong to nobody — rentals, open sessions, activities that take no bookings — so the classification can be looked at rather than trusted. Choosing a course records a permanent manual assignment and re-runs the matching over stored data at once, without a request to iSport. The menu carries a count.
- Make-up lessons can be assigned the way the rest of their series is, from the row or for every repeat at once. A make-up slot is a weekly fixture — same name, weekday, hour and room — so once a person has said which course one of them stands in for, the repeats need a press rather than a hunt through a hundred-item list. Where two occurrences of one series were assigned to two different courses nothing is offered, because then the series is not a series; and the trainer is deliberately not compared, since the timetable names one some weeks and not others. Nothing is written without the press.
- A Czech translation of everything the admin shows, with the `.pot` beside it, loaded from the plugin's own `languages` folder on `init` before the post type registers its labels. The site this is built for is Czech and its manager should not have to read English to record which course a make-up lesson belongs to.
- Admin: an **iSport → Make-up lessons** screen where a site manager ties each make-up occurrence to the course it stands in for, with the date, time, room and trainer beside it, filters for the unassigned and the assigned, and a button that records the suggestions the names allow. The menu carries a count of the ones still unassigned, because these arrive a few at a time and nobody opens a screen on the off chance something is waiting on it. It is a content screen, not a settings one: recording which course a lesson belongs to is running the site, not configuring the plugin.
- `MakeupResolver::suggest_by_names()` answers the same question from course names and ids rather than course records, so a screen can ask it without reaching the network. Both callers file and read the suggestion under the same key, which a test now pins: a screen computing the key one way while the resolver filed it another would quietly never show a suggestion.
- Retention forgets the manual assignments and make-up links of the occurrences it purges, and only those: an id missing from the table may simply not have been retrieved yet, and forgetting that link would undo somebody's work. The lookup runs only where a link exists to lose.
- Make-up lessons are their own category rather than being lumped in with activities that take no bookings. They are a replacement for a class somebody missed, which is a different thing to show and a different thing to count.
- Admin: an **iSport** menu with an overview screen showing what is stored, how the last runs went, and how many requests have been made this hour — the remote system belongs to somebody else, so that figure should be readable off a screen rather than estimated.
- Admin: a settings screen covering the connection, the term, refresh intervals, retention, display defaults and the list of activities that take no bookings. Every field is written through the same validating setter the command line uses, so the form cannot store an address the client would refuse.
- An **iSport manager** role with `cscs_manage_content`, granted to editors and administrators. `cscs_manage_design`, which covers settings and anything that reaches the network, stays with administrators. The split is enforced when a request is handled, not by hiding fields: hiding is a courtesy, a capability check is the rule.


### Fixed
- **The plugin's stylesheet never reached a Divi theme builder template.** It is enqueued where something renders — the shortcode, the block, the plugin's own course and trainer templates — and a theme builder layout is none of those: it replaces the template, so nothing asked for the file. Every table on a trainer's page was therefore drawn without its rule, its spacing or the fold that turns it into one card per row on a telephone, and nothing said so. Both Divi modules now ask for it when they render.
- The **picture panel never appeared in a block**. The catalogue the editor script reads had every field's name, kind and heading in it and not the one flag that says "this field is a picture", so the panel that chooses the size, the alternative text and the link was skipped on the two fields that have one. It was written and registered and reachable by nothing.
- **Design settings now take effect in Divi's builder while you are in it**, rather than only after the page is saved. Nothing about the modules was wrong on the page — every setting was stored and rendered — but the canvas never changed, which makes a builder you cannot design in. Two things were missing, and both fail without a word. Divi decides from an attribute's `elementType` which style components it gets, and an attribute that does not declare one gets none; the heading, the value and the picture now say what kind of element they are, the way Divi's own modules do. And a module's CSS has to be written with its order class already set on it, or the rules come out beginning with a space and belong to nothing; the modules now set their classes before asking for their styles, and render them inside the module the way Divi's own do. Verified in an ordinary page and in a theme builder template, on typography and on a picture's corners.
- The **Photograph** and **Course picture** modules behave like a picture rather than like a price. A picture is a different shape from a number, and giving both the same panel is what left them without the settings anybody would look for: which of WordPress's sizes to serve, what the picture says to a reader who cannot see it, and whether it is a link — to its own page, to the full-size file, or anywhere you name. The border, the corners, the shadow and the framing now sit on the `img` itself, which is where Divi's own Image module puts them and why rounding a photograph's corners on the module did nothing.
- Declaring those settings was only half of it. Without `styleProps` Divi knows which element a field belongs to and still has nowhere to write its CSS, so every one of them accepted a value and did nothing; the module now emits the picture's styles alongside the heading's and the value's. A setting that is offered and quietly ignored is worse than one that is not offered at all.
- The content panel was still in English while everything around it was translated. The fields are written in English in the generated module files and were handed to the builder that way; their wording is the site's business, so it is now translated at runtime like the module titles.
- A field with nothing to say left a gap behind it. It printed nothing, correctly, but the Divi module wrapper around it stayed — and a Divi column is a flex container with a gap between its children, so a module of no height still cost one gap. On a trainer who had filled in no interests, that was a hole between two sections with nothing on the page to explain it. An empty field now leaves the page entirely, wrapper and all; the listing module does the same.
- A field in a Divi theme builder template said the page was neither a course nor a trainer, on a page that plainly was one. The module asked `get_post()`, and while a theme builder layout renders, the global post **is the layout** — so every field on the one kind of page the option exists for reported the one thing that could not be true. It now asks `get_queried_object()`, which is what the visitor asked for and does not move.
- While a theme builder template is being designed there is no particular course to show, so every field previewed as "this page is neither" — true, and useless, since a page whose every element refuses to appear cannot be laid out. The builder is now shown a real record, the way Divi shows sample text in its own dynamic modules. Only ever in the editor: the fallback is reached in a REST request from somebody who may edit posts, and a visitor's page is not a REST request.
- The builder said "choose one in the module settings" where a field simply had nothing to print, which sent people looking for a setting to change. It now says the field is empty for this record and will not appear on the page — which is what is happening. The two builder strings are handed over with the module metadata rather than fetched through `wp.i18n`: the Visual Builder loads its packages through Divi's own manager, and a handle WordPress never registered is one `wp_set_script_translations` cannot reach, so they stayed English while everything around them was translated.
- Structured data was never printed on a course page. `wp_head` runs before the loop, and the guard asked `in_the_loop()`, which is always false there — the one kind of bug that leaves no trace on the page it is missing from.
- A post type added in an update brings URLs with it, and those only work once the rewrite rules have been rebuilt. Activation was the obvious moment and the wrong one — an update is not an activation, and every trainer page on an already-running site would have answered 404 with nothing to say why. The rules are now rebuilt once per version that adds a URL, the same way the schema and the capabilities are.
- Continuous integration: the first run failed every job. `npm ci` had no lock file to install from and there was no JavaScript to build, `phpunit/phpunit` and `phpstan/phpstan` were missing from the development requirements, and PHPStan was pointed at a `templates` directory that does not exist yet.
- Coding standards: every violation reported by PHP_CodeSniffer against the `WordPress`, `WordPress-Docs` and `PHPCompatibilityWP` rulesets, verified locally against the same tool versions the pipeline resolves.
- Static analysis: WP-CLI stubs and the WordPress time constants are now declared, so PHPStan resolves every symbol at level 6.
- The failure circuit no longer punishes a repair. Changing a setting that affects requests — the base URL, a timeout, the retry or ceiling values — closes the circuit and drops the cached responses, and `wp cscs api reset` does the same on demand. Previously, correcting a bad base URL meant being told for the next half hour that requests were paused.
- The client no longer refuses a response because of its `Content-Type`. The iSport endpoints are hand-written PHP that announces JSON as `text/html`, so the check rejected the live system while accepting nothing extra: the real protection was always that the body decodes to an array. A body opening with a tag is now reported as an error page rather than as a JSON syntax error, and a leading byte order mark no longer defeats decoding.
- `readme.txt` no longer promises screenshots that are not in the repository, and declares the current WordPress release.
- `yoast/phpunit-polyfills` removed: it caps PHPUnit at 9 and is only needed by the WordPress core test suite, which this plugin does not use.
- Plugin Check now runs against a build of the WordPress.org artefact rather than the repository, with the slug supplied explicitly, so it sees what would actually be submitted instead of the development tree.
- The redundant PHP version guard is gone. WordPress enforces `Requires PHP` itself and refuses to activate a plugin the server cannot run, so the check was an unreachable branch that static analysis rightly flagged.

### Changed
- A course's page lives at `/kurz/…` and a trainer's at `/trener/…`, not `/course/…` and `/trainer/…`. The plugin's own vocabulary stays English — that is for whoever maintains it — but an address is something a reader sees, and nothing a reader sees should be in a language the site is not written in. `cscs_course_rewrite_slug` and `cscs_trainer_rewrite_slug` filter them, and the rewrite rules rebuild themselves on the next request.

- The repository is renamed to match the plugin slug, so a checkout directory is never mistaken for the plugin name.
- Every quality gate now runs even when an earlier one fails, and each writes its output to the run summary. One push therefore reports every problem at once, and the results are readable from the run page without downloading an artifact.
