# Contributing

Thanks for your interest in improving this plugin.

## Getting set up

```bash
git clone https://github.com/lukasista/wpdissi.git course-schedule-connector
cd course-schedule-connector
composer install
npm ci
npm run build
```

A local WordPress install is expected at `wp-content/plugins/course-schedule-connector`. A symlink works fine.

## Branching

- `main` is always releasable.
- Work happens on `feature/<short-name>` or `fix/<short-name>`.
- Rebase before opening a pull request; keep history readable.

## Commit messages

[Conventional Commits](https://www.conventionalcommits.org/):

```
feat(sync): add manual re-match for unmatched lessons
fix(render): escape trainer name in the calendar tooltip
docs(user-guide): describe the semester setting
```

Types in use: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `build`, `ci`.

## Coding standards

PHP follows the [WordPress Coding Standards](https://developer.wordpress.org/coding-standards/wordpress-coding-standards/). This is enforced, not suggested:

```bash
composer run lint       # check
composer run lint:fix   # auto-fix
composer run analyse    # PHPStan level 6
```

Non-negotiable rules:

- Every function, class, hook, option, meta key, table name, CSS class and JS handle is prefixed `cscs_` / `CSCS` / `cscs-`.
- Every input is sanitised on the way in, every output escaped on the way out. No exceptions for "trusted" data — the remote API is not trusted.
- Every state-changing request checks a capability **and** verifies a nonce.
- Every database query uses `$wpdb->prepare()`.
- Every user-facing string is wrapped in a translation function with the `course-schedule-connector` text domain. No variables as the text domain.
- No direct file access: every PHP file starts with a `defined( 'ABSPATH' ) || exit;` guard.
- No `error_log()`, `var_dump()` or `console.log()` in committed code.

## Tests

Add or update a test for any behaviour you change:

```bash
composer run test
```

Anything that parses API responses must have a test using a fixture in `tests/fixtures/`, not a live request.

## Pull requests

A pull request must:

1. pass PHPCS, PHPStan, PHPUnit and Plugin Check in CI,
2. update `CHANGELOG.md` under `## [Unreleased]`,
3. update the relevant document in `docs/` if behaviour visible to users or developers changed,
4. describe how it was tested.

## Translations

Do not edit `.pot` by hand — it is regenerated by the build. New strings only need the correct text domain.
